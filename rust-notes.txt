====================================
Rust 공부 노트
====================================

이 파일은 배울 때마다 이어서 채워짐.

------------------------------------
[1] 왜 Rust인가 — 안전 철학
------------------------------------

C의 큰 문제 두 가지:
  1) 버퍼 오버플로우 (배열 밖에 써버림)
  2) use-after-free (반납한 메모리를 또 씀)
둘 다 공격자가 프로그램을 조종하는 통로.

각 언어의 답:
  - C     : "네가 알아서 해." → 뚫림
  - Java/C#/Python : 가비지 컬렉터가 실행 중에 청소 → 안전한데 느림, 예측 불가
  - Rust  : 컴파일 때 규칙으로 강제 + 실행 중 검사도 병행

Rust의 방식은 두 갈래:
  - 컴파일 때 알 수 있는 것 → 컴파일 거부 (소유권/빌림)
  - 실행해봐야 아는 것    → 실행 중에 panic으로 즉시 중단

배열 인덱스 예:
  let arr = [1,2,3,4,5];
  let i = 10;
  arr[i];   // 💥 panic: index out of bounds

C는 그냥 옆칸 덮어써서 뚫림 → 조종당함.
Rust는 그 자리에서 멈춤 → 최악(조종당함)을 중간(그냥 꺼짐)으로 바꾼 것.

------------------------------------
[2] 소유권 (Ownership) — 컴파일 때 막는 것
------------------------------------

핵심 규칙:
  "모든 값은 주인이 딱 한 명. 주인이 사라지면 값도 같이 사라진다."

예시:
  let s1 = String::from("hello");   // s1이 주인
  let s2 = s1;                      // 주인이 s2로 넘어감 (move)
  println!("{}", s1);               // ❌ 컴파일 에러
  // error: borrow of moved value: `s1`

이 규칙 하나로 C의 세 가지 문제가 통째로 사라짐:
  - 안 치움      → 주인 죽을 때 무조건 치우므로 불가능
  - 두 번 치움   → 주인이 하나뿐이므로 불가능
  - 치웠는데 씀 → 주인 죽으면 그 이름도 못 씀

전부 실행 전(컴파일 때)에 잡음 → 실행 중 검사 없음 → C만큼 빠름.

------------------------------------
[3] 빌림 (Borrowing) — & 참조
------------------------------------

문제: 주인 한 명 규칙이면 함수에 넘길 때마다 뺏김. 불편.

해결: 완전히 넘기지 말고 "잠깐 빌려주기". 그게 & 기호.

  fn print_it(s: &String) {   // 빌리기만 받음
      println!("{}", s);
  }
  let msg = String::from("hello");
  print_it(&msg);            // 빌려줌
  println!("{}", msg);       // ✅ 주인은 여전히 msg

책 빌려주기랑 똑같음.
  - msg   → 줘버림 (내 책장에서 사라짐)
  - &msg  → 빌려줌 (여전히 내 거)

빌림의 두 규칙:
  1) 읽기 빌림(&T)  → 몇 개든 동시에 OK
  2) 쓰기 빌림(&mut T) → 딱 하나만, 그때는 다른 빌림도 금지

한 문장:
  "여러 명이 읽는 건 되는데, 쓰는 사람이 있으면 그 사람 혼자여야 한다."

  let mut s = String::from("hello");
  let r1 = &s;      // OK
  let r2 = &s;      // OK (읽기는 여러 개 가능)
  let w1 = &mut s;  // 여기서 위 r1, r2가 살아있으면 ❌

왜 중요? → 데이터 레이스(data race) 원천봉쇄.
  두 스레드가 동시에 같은 데이터에 쓰는 상황이 컴파일 때 아예 불가능.
  실행 중 락 필요 없음. "컴파일 통과 = 데이터 레이스 없음" 보장.
  이게 Rust의 "Fearless Concurrency".

정리표:
  s        →  소유권 자체     (주인 한 명)
  &s       →  읽기 빌림       (여러 명 OK)
  &mut s   →  쓰기 빌림       (딱 하나, 다른 빌림 금지)

------------------------------------
[4] 라이프타임 (Lifetime) — 참조가 원본보다 오래 살면?
------------------------------------

문제: C에서 이런 게 됨 (댕글링 포인터)
  {
      char x = 'A';
      p = &x;
  }                  // x 죽음
  printf("%c", *p);  // 💥 죽은 x 참조

Rust는 컴파일 때 막음:
  let r;
  {
      let x = 5;
      r = &x;
  }                  // x 죽음
  println!("{}", r); // ❌ `x` does not live long enough

원리: 모든 참조에 보이지 않는 '수명(lifetime)' 이 붙어있음.
      borrow checker가 "참조가 원본보다 오래 살면 안 됨"을 강제.

대부분 자동 판정. 근데 함수가 참조를 받아 참조를 돌려줄 때는
컴파일러가 헷갈려서 이름을 직접 붙여줘야 함:

  fn longer<'a>(a: &'a str, b: &'a str) -> &'a str {
      if a.len() > b.len() { a } else { b }
  }

'a는 라벨. 뜻: "a, b, 반환값 모두 같은 수명 'a짜리."
즉 "두 입력 중 짧게 사는 쪽만큼만 결과가 살 수 있다"고 알려주는 것.

------------------------------------
[요약] Rust 삼종세트
------------------------------------
                뭘 막나                C의 문제
  소유권      두 번 해제, 안 해제      double free, memory leak
  빌림        동시 쓰기                 data race
  라이프타임  죽은 것 참조              use-after-free, dangling pointer

세 개가 컴파일 때 협력 → C의 메모리 버그를 실행 오버헤드 0으로 없앰.
이게 Rust가 시스템 프로그래밍의 자리를 뺏은 이유.
