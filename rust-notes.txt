====================================
Rust 공부 노트
====================================

이 파일은 배울 때마다 이어서 채워짐.

------------------------------------
[1] 왜 Rust인가 — 안전 철학
------------------------------------

C의 큰 문제 두 가지:
  1) 버퍼 오버플로우 (배열 밖에 써버림)
  2) use-after-free (반납한 메모리를 또 씀)
둘 다 공격자가 프로그램을 조종하는 통로.

각 언어의 답:
  - C     : "네가 알아서 해." → 뚫림
  - Java/C#/Python : 가비지 컬렉터가 실행 중에 청소 → 안전한데 느림, 예측 불가
  - Rust  : 컴파일 때 규칙으로 강제 + 실행 중 검사도 병행

Rust의 방식은 두 갈래:
  - 컴파일 때 알 수 있는 것 → 컴파일 거부 (소유권/빌림)
  - 실행해봐야 아는 것    → 실행 중에 panic으로 즉시 중단

배열 인덱스 예:
  let arr = [1,2,3,4,5];
  let i = 10;
  arr[i];   // 💥 panic: index out of bounds

C는 그냥 옆칸 덮어써서 뚫림 → 조종당함.
Rust는 그 자리에서 멈춤 → 최악(조종당함)을 중간(그냥 꺼짐)으로 바꾼 것.

------------------------------------
[2] 소유권 (Ownership) — 컴파일 때 막는 것
------------------------------------

핵심 규칙:
  "모든 값은 주인이 딱 한 명. 주인이 사라지면 값도 같이 사라진다."

예시:
  let s1 = String::from("hello");   // s1이 주인
  let s2 = s1;                      // 주인이 s2로 넘어감 (move)
  println!("{}", s1);               // ❌ 컴파일 에러
  // error: borrow of moved value: `s1`

이 규칙 하나로 C의 세 가지 문제가 통째로 사라짐:
  - 안 치움      → 주인 죽을 때 무조건 치우므로 불가능
  - 두 번 치움   → 주인이 하나뿐이므로 불가능
  - 치웠는데 씀 → 주인 죽으면 그 이름도 못 씀

전부 실행 전(컴파일 때)에 잡음 → 실행 중 검사 없음 → C만큼 빠름.

------------------------------------
[3] 빌림 (Borrowing) — & 참조
------------------------------------

문제: 주인 한 명 규칙이면 함수에 넘길 때마다 뺏김. 불편.

해결: 완전히 넘기지 말고 "잠깐 빌려주기". 그게 & 기호.

  fn print_it(s: &String) {   // 빌리기만 받음
      println!("{}", s);
  }
  let msg = String::from("hello");
  print_it(&msg);            // 빌려줌
  println!("{}", msg);       // ✅ 주인은 여전히 msg

책 빌려주기랑 똑같음.
  - msg   → 줘버림 (내 책장에서 사라짐)
  - &msg  → 빌려줌 (여전히 내 거)

빌림의 두 규칙:
  1) 읽기 빌림(&T)  → 몇 개든 동시에 OK
  2) 쓰기 빌림(&mut T) → 딱 하나만, 그때는 다른 빌림도 금지

한 문장:
  "여러 명이 읽는 건 되는데, 쓰는 사람이 있으면 그 사람 혼자여야 한다."

  let mut s = String::from("hello");
  let r1 = &s;      // OK
  let r2 = &s;      // OK (읽기는 여러 개 가능)
  let w1 = &mut s;  // 여기서 위 r1, r2가 살아있으면 ❌

왜 중요? → 데이터 레이스(data race) 원천봉쇄.
  두 스레드가 동시에 같은 데이터에 쓰는 상황이 컴파일 때 아예 불가능.
  실행 중 락 필요 없음. "컴파일 통과 = 데이터 레이스 없음" 보장.
  이게 Rust의 "Fearless Concurrency".

정리표:
  s        →  소유권 자체     (주인 한 명)
  &s       →  읽기 빌림       (여러 명 OK)
  &mut s   →  쓰기 빌림       (딱 하나, 다른 빌림 금지)

------------------------------------
[4] 라이프타임 (Lifetime) — 참조가 원본보다 오래 살면?
------------------------------------

문제: C에서 이런 게 됨 (댕글링 포인터)
  {
      char x = 'A';
      p = &x;
  }                  // x 죽음
  printf("%c", *p);  // 💥 죽은 x 참조

Rust는 컴파일 때 막음:
  let r;
  {
      let x = 5;
      r = &x;
  }                  // x 죽음
  println!("{}", r); // ❌ `x` does not live long enough

원리: 모든 참조에 보이지 않는 '수명(lifetime)' 이 붙어있음.
      borrow checker가 "참조가 원본보다 오래 살면 안 됨"을 강제.

대부분 자동 판정. 근데 함수가 참조를 받아 참조를 돌려줄 때는
컴파일러가 헷갈려서 이름을 직접 붙여줘야 함:

  fn longer<'a>(a: &'a str, b: &'a str) -> &'a str {
      if a.len() > b.len() { a } else { b }
  }

'a는 라벨. 뜻: "a, b, 반환값 모두 같은 수명 'a짜리."
즉 "두 입력 중 짧게 사는 쪽만큼만 결과가 살 수 있다"고 알려주는 것.

[요약] Rust 삼종세트
------------------------------------
                뭘 막나                C의 문제
  소유권      두 번 해제, 안 해제      double free, memory leak
  빌림        동시 쓰기                 data race
  라이프타임  죽은 것 참조              use-after-free, dangling pointer

세 개가 컴파일 때 협력 → C의 메모리 버그를 실행 오버헤드 0으로 없앰.
이게 Rust가 시스템 프로그래밍의 자리를 뺏은 이유.

------------------------------------
[5] Copy vs Move — 어떤 건 대입해도 안 죽음
------------------------------------

정수, bool, char 같은 작은 값 → 대입 시 자동 복사, 원본 살아있음
  let x = 5;
  let y = x;
  println!("{}", x);   // ✅ OK

String, Vec 등 큰 값 → 대입 시 move, 원본 죽음
  let s1 = String::from("hi");
  let s2 = s1;
  println!("{}", s1);  // ❌ borrow of moved value

기준: 복사가 진짜 싼가?
  - 싸면 (Copy trait) → 자동
  - 비싸면 → .clone() 명시적으로 불러야 함
"자동으로 몰래 비싼 짓 하지 않는다"가 Rust 철학.

------------------------------------
[6] mut — 기본은 못 바꿈
------------------------------------

Rust의 기본은 immutable(못 바꿈). 바꾸려면 mut로 명시적 허락.

  let mut s = String::from("hi");    // ← 변수도 mut
  add_bang(&mut s);                   // ← 빌려줄 때도 &mut
  fn add_bang(x: &mut String) { ... } // ← 받는 쪽도 &mut

세 군데 다 표시해야 함. 대신 코드 읽을 때
"얜 안 바뀜"이 기본이라 실수가 확 줄어듦.

------------------------------------
[7] 함수 파라미터 고르는 기준
------------------------------------

  함수가 값을...              쓸 것:
  ─────────────────────────────────────
  주인이 돼야 함 (드묾)      String       (소유권 넘김)
  읽기만 함 (대부분)          &String       (읽기 빌림)
  바꿔야 함                   &mut String   (쓰기 빌림)

거의 항상 &가 정답. String 그대로 받는 건 진짜 소유권을 뺏어야 할 때만.

컴파일러도 이걸 안내해줌:
  "consider changing this parameter to borrow instead
   if owning the value isn't necessary"

------------------------------------
[8] Option — null을 없앤 방법
------------------------------------

다른 언어의 문제: null 검사 까먹으면 크래시 (NullPointerException 등).
                  Tony Hoare 본인이 "10억 달러짜리 실수"라고 사과함.

Rust엔 null이 없음. 대신 Option<T>:
  Some(값) — 값이 있음
  None    — 값이 없음

  fn find_user(id: i32) -> Option<String> {
      if id == 1 { Some(String::from("영희")) } else { None }
  }

Option<String>은 그냥 String이 아님. 껍데기 씌워진 상태.
쓰려면 반드시 안을 꺼내야 함(컴파일 강제).

------------------------------------
[9] match — 모든 경우 강제로 다루기
------------------------------------

  match user {
      Some(name) => println!("찾음: {}", name),
      None       => println!("없음"),
  }

경우 하나라도 빼먹으면 컴파일 에러:
  error[E0004]: non-exhaustive patterns: `None` not covered

의미:
  - 리팩토링해서 새 경우 추가돼도 컴파일러가 다 짚어줌
  - "몰래 지나가는 case" 불가능 (switch의 fall-through 문제 없음)

------------------------------------
[10] Result — 예외를 없앤 방법
------------------------------------

Option이 "있음/없음"이면 Result는 "성공/실패":
  Ok(값)   — 성공
  Err(이유) — 실패

  fn divide(a: i32, b: i32) -> Result<i32, String> {
      if b == 0 { Err(String::from("0 나눗셈")) }
      else      { Ok(a / b) }
  }

함수 시그니처 -> Result<i32, String> 만 봐도
"성공하면 i32, 실패하면 String 이유가 온다"가 보임.
숨겨진 예외 던지기 불가능.

------------------------------------
[요약2] Rust의 안전 전략
------------------------------------
                 다른 언어              Rust
  없음 표현     null (숨김)             Option<T> (타입에 박음)
  실패 표현     예외 (숨김)             Result<T,E> (타입에 박음)
  분기 처리     switch (case 빼먹음)   match (다 안 다루면 컴파일 X)

핵심: "위험한 걸 타입에 박아넣기". 그러면 컴파일러가 강제.
결과: 런타임 크래시가 컴파일 에러로 이동.
      실행 안 해봐도 컴파일만 통과했으면 이 종류 버그 없음이 보장.

------------------------------------
[11] enum — Rust의 슈퍼파워
------------------------------------

다른 언어 enum: 이름 붙인 숫자 (RED=0, GREEN=1...)
Rust enum: 여러 종류 중 하나 + 각 종류가 자기 데이터를 가짐

  enum Message {
      Quit,                            // 데이터 없음
      Move { x: i32, y: i32 },         // 이름 붙은 필드
      Write(String),                   // 튜플식
      Color(u8, u8, u8),
  }

한 변수가 "여러 다른 모양 중 하나"를 나타냄.
다른 언어에서 이걸 하려면 클래스 상속 + instanceof 검사가 필요.

------------------------------------
[12] Option/Result의 정체
------------------------------------

사실 그냥 enum임. 표준 라이브러리에 이렇게 정의됨:

  enum Option<T> {
      Some(T),
      None,
  }

  enum Result<T, E> {
      Ok(T),
      Err(E),
  }

<T>, <E>는 "아무 타입이나 넣을 수 있음" = 제네릭.
C++ 템플릿, Java Generics랑 같은 개념.

특별 문법이 아니라 enum이라는 도구 하나로 표현된 것뿐.

------------------------------------
[13] "불법 상태를 표현 불가능하게 만들기"
------------------------------------

배달 앱 예:
  enum OrderStatus {
      Pending,
      Confirmed { order_id: u32 },
      Delivering { driver: String },
      Delivered { rating: u8 },
      Cancelled { reason: String },
  }

Pending 상태엔 기사 이름이 아예 존재 불가능.
Delivered에 취소 사유도 존재 불가능.
잘못된 조합이 문법적으로 표현 안 됨.

Java 방식이었으면:
  class Order {
      String status;
      String driver;         // null일 수도 있고 아닐 수도
      Integer rating;        // ...
      String cancelReason;   // ...
  }
→ Pending인데 driver가 있는 상태가 표현 가능 → 버그 온상.

이걸 "make illegal states unrepresentable"이라고 함.
Rust 코드가 안전한 진짜 이유.

+ 나중에 새 variant 추가하면 match가 없는 곳 다 자동 검출.
  리팩토링이 안 무서움.
